# 写事件的规则（给写某一批的帮手）

你负责一批材料。先读 `brief.md`：摘要对象是谁、谁来读、怎么称呼、哪些标签能用、「等这个人」怎么写，还有你这批要读的材料包、要写的 JSON 和自查命令的绝对路径，都在那里。下文的「这个人」就是摘要对象。

## 材料长什么样

每个会话以 `##### SESSION <agent>:<id>` 开头，下面是：分组、原标题、创建时间、这个人的触发消息编号、回话的助手，然后逐轮「时间 · 谁触发 · taskId 前 8 位」+「问」+「答」。

- 「答」是助手回答的结尾部分，开头可能有几句英文过程话，忽略。
- 「续跑」轮是后台帮手回来接着做，结果常在这里，跟前一轮算同一件事。
- 「答：（空）」：看下一轮或续跑里有没有交代；都没有就写「材料里看不出结果」，状态按能看到的最后一轮定。
- 别人在同一会话里说的轮次已经去掉，只留计数，不要写进去。
- 老会话会附「底库里这个会话已有的事」，只供参考：新轮次接着旧事做下去的，写一个新 event，标题可以写「接着…」，judgement 里说清这次比上次多了什么、哪件旧事这次收口了；不要重写旧事。只有续跑轮的会话，也写一个 event 说续跑交了什么。

## 交什么

一个 JSON 数组，材料里每个会话一项，一个都不能漏，也不能多：

```json
[
  {
    "key": "claude:89036e6c-0ac0-440d-97c7-13772f63af22",
    "title": "可读的会话标题：说明实际做了什么（15–30 字）",
    "orig_title": "材料里的原标题（照抄，去掉换行、uid 和消息编号，最多 60 字）",
    "assistant": "照抄材料里的「回话的助手」；写着「材料里看不出」的才自己从答里判断",
    "source": "用户主动 | 明确派工 | 自动任务 | 自动派生",
    "events": [
      {
        "title": "可读的活动标题（一句话，10–25 字）",
        "start": "2026-10-27 11:43",
        "end": "2026-10-27 11:58",
        "trigger": "用户主动 | 明确派工 | 自动任务 | 自动派生",
        "one_line": "活动一句话：日常语言，这个人当时要什么、助手做了什么",
        "summary": "高层总结：这件事带来了什么变化（一两句）",
        "status": "已完成 | 进行中 | 中断 | 失败 | 阻塞或等待 | 等待验收 | 无新增产物",
        "evidence": ["1–3 条可核验的结果：具体数字、结论、产物文件名（本机有/本机没找到）"],
        "judgement": "这件事意味着什么（不复述状态，不说套话）",
        "next": "有依据的复核点；没有就写「无」",
        "tag": "#从 brief.md 的标签里选一个",
        "clues": "细节线索：taskId 前 8 位、触发消息编号、验证限制等",
        "turns": ["e913f31d", "0f190edf"]
      }
    ]
  }
]
```

- source：这个人自己在私信、群里、工作台说的 → 用户主动；助手按这个人的话派出去的任务会话 → 明确派工；定时任务 → 自动任务；助手自动接这个人的话 → 自动派生。每个 event 的 trigger 按那件事开头那一轮填：派出去的任务里这个人后来追问、催进度、补要求，仍算明确派工；在同一会话里另起一件新事，才按新事那轮填。
- turns 只能填材料里这个会话出现过的 taskId 前 8 位。

## 怎么拆成 events

- 同一会话里不同的事拆开；同一件事来回几轮（追问、纠正、「你继续」「网页呢」）合成一个 event，不按消息机械拆。
- 时间用材料里的真实轮次时间：start = 这件事第一轮开始，end = 最后一轮（含续跑）结束。北京时间，`YYYY-MM-DD HH:MM`。窗口规则见 brief.md。
- 只是来问另一件任务进度的会话：照样写一个 event，judgement 里点明是哪件事的进度，证据不要把那件事的结果再抄一遍。
- 定时任务会话：整个会话合成一个 event，写清这次窗口里触发了几次、跑完几次、哪几次中断及原因（材料里看得到的）、最近一次交了什么。这个人在定时会话里插话问别的事，单独一个 event。

## 状态怎么标

| 情况 | status | next |
|---|---|---|
| 回答了问题、交了东西 | 已完成 | 无，或有依据的复核点 |
| 交给别的会话或助手、还没做出来 | 进行中 | 「结果在派出去的那个会话里」 |
| 做完了，等这个人看、试、验收 | 等待验收 | 以 brief.md 里的「等…」开头，写清看什么 |
| 助手说要这个人定、要别人回话、被外部卡住 | 阻塞或等待 | 等这个人的以 brief.md 里的「等…」开头；等别人的写「等 X …」 |
| 只有计划没产物 | 无新增产物 | 无 |
| 只负责派活、转交的会话 | 派出去那件在同一批材料里：已完成，标题写「把…派给…」；不在：进行中 | 已完成写无；进行中写「结果在派出去的那个会话里」 |
| 材料里有中断标记 | 中断 | 卡在哪 |
| 明确失败 | 失败 | 原因 |

- 已完成和等待验收怎么分：交的东西要这个人看过、点头才算数（草稿 PR 等合并、稿子等定版、改动等他试）→ 等待验收；不用他再动手就算数 → 已完成，next 里的复核点只是可选的。
- 定时任务照常跑完、交了东西 → 已完成；交的东西里明确请这个人拍板 → 阻塞或等待，next 写等他定什么。
- 等的事带着时点（「今晚」「明天上午」），到材料截止时已经过了、材料里又看不出后来定没定：照样标阻塞或等待，next 末尾加「材料里看不出后来定没定」。
- 只派活、转交的会话：证据只写派给了谁、带了什么要求，不把派出去那件的结果再抄一遍。
- 「工具回了 completed」不等于目标完成；助手自报「测试通过」要写「会话自报」。
- 过去的建议、推测、报价不当事实；没被这个人接受的建议不写成待办。
- 这个人后来纠正过的，以最新纠正为准。

## 写法

- 全部中文，短句，说人话。读的人见 brief.md：给本人看称「你」，给别人看直接写名字。
- 证据要具体：数字、结论、产物文件名。本机文件可以用一两条 `ls` / `find <会话工作目录> -maxdepth 3 -name '名字*'` 核一下，写「本机有」或「本机没找到」；核不了就不写。每个会话最多两三条命令，不要大范围搜。产物不是本机文件（空间文档、PR、网页链接、作为聊天附件发出的图和文件）就写它是什么，如「空间文档《年终活动方案》」「PR 7778，已合并」「设计稿 9 张，作为附件发出」，不写本机有没有。
- 正文（title、one_line、summary、evidence、judgement、next）里不贴文件路径、消息编号（`room#123`）、uid、字段名；这些只放 clues。PR 写「PR 7778」，不带 #。
- 拿不准就写「材料里看不出」，不要猜。

## 隐私（必须守）

- 只写这一批材料里有的东西，不去翻别的会话、私信、群来补。
- 别人私信里说的话只写结论，不引原话；别人（同事、客户）在会话里说的话不写进来。
- 给本人出时，这个人自己的话可以短引，一句以内。替别人出（brief.md 里「读摘要的人」不是本人）时，谁的原话都不引，这个人自己的话也只写意思，如写「问报表在哪下载」，不写他问的原句。
- 不写邮箱、手机号、密钥、带 token 的链接、账号密码。公开的社媒账号名、产品名可以写。

## 范例（一个 event，内容是编的，只看写法）

```json
{
  "title": "把三档会员价的影响做成一页对照",
  "start": "2026-01-05 10:20", "end": "2026-01-05 10:48",
  "trigger": "明确派工",
  "one_line": "调价前要一页让大家一眼看懂影响多大，助手拿上个月的真实用量算了三档价钱",
  "summary": "调价讨论第一次有了同一把尺子：中档涨价后，重度用户每月多付约四成",
  "status": "等待验收",
  "evidence": ["页面结论：轻度用户几乎不受影响，重度用户每月多付约四成", "样本：上个月有用量的 120 个账号", "产物：会员调价对照.html（本机有）"],
  "judgement": "定调价时间要用的对照有了；同时问的「影响哪几个大客户」这个会话没做",
  "next": "等你看完对照页定用哪一档",
  "tag": "#定价与额度",
  "clues": "taskId 见 turns；触发消息编号、取数口径写在这里",
  "turns": ["xxxxxxxx"]
}
```

## 交回

写完后跑 brief.md 末尾的自查命令（绝对路径，N 换成批号）：会话数要等于材料里 `##### SESSION` 的个数。最后回一行：会话数、event 数、有没有拿不准的。
